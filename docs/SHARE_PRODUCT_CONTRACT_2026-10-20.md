# FloatClip：三端统一产品与发布规范

用户最新决策：iPad 使用 PWA；节点放在小主机；网页用独立账号认证并保持登录。
Android 与 Windows 继续发展原生近距离传输，不再推进 iPad TestFlight 分发。

## 当前实际状态

- PWA 0.2.0：独立账号、30 天登录保持、完整公共外壳缓存、设置内更新检查，
  支持 WebRTC 直连和经小主机的端到端加密转发。入口 `https://clip.wmy-cloud.cn`。
- 原生 Android/Windows 仍为 0.4.0，保留 FCP2/FCS1 TLS 局域网共享。
  本轮未重新发布它们的安装包。它们的浏览器可使用相同 PWA 与 iPad 互通。
- 原生与网页的协议适配仍待实现，不能把分别支持共享写成已经原生互通。
  蓝牙配对和 Wi-Fi Direct 也尚未作为可用功能发布。

## 界面契约

`web/shared/design-tokens.json` 是三端颜色与页面命名的共同基准。保留既有
蓝白配色及深色/浅色/跟随系统，三个主入口统一为“共享、设备、设置”。
平板/桌面采用侧栏，窄屏采用底栏；设置首页为分组入口，具体操作进入详情。
状态文案必须分别表示“设备加密直连”和“经小主机加密转发”。
不把“端到端加密”“本地直连”“去中心化”当作同一个状态。

`scripts/check-share-contract.py` 检查三端配色、版本记录及共用功能声明，
GitHub 工作流在相关代码或更新源改变时运行。颜色以当前已发布原生端为准，
不为统一外观而破坏平台的触控、键盘、文件选择和无障碍习惯。

## 后续功能同步

1. 同一共享功能先更新共同契约和三端验收用例，再分别实现平台适配。
2. 共用功能的 `featureContract` 必须列出 Android、Windows、Web 三端，
   已纳入共同发布的功能均需实现，不能只更新一个平台后标为整体完成。
3. 传输技术允许不同：iPad Web 受浏览器能力约束，Android/Windows 可采用
   蓝牙或 Wi-Fi Direct。平台独有能力须单列，不伪装成三端共同能力。
4. 独立维护安装包版本号，用一个 `releaseTrain` 关联本轮发布；版本号相同
   不能替代功能一致性。更新源同时记录原生安装包与 PWA 的实际版本和入口。
5. 发布说明需同时写明三端变更、兼容的协议、自动测试和真机待验项目。
   修改协议时保留旧版本协商或给出可执行的迁移顺序。

本轮为 PWA 新增节点入口；原生新硬件能力不随网页部署自动获得。下一项共享
通信工作应先增加 `web-v1` 的原生协议适配，保留旧的原生 LAN 模式，再把同一
会话模型接到不同底层传输。统一的确认、文件校验、限速、取消和更新行为不分叉。

## Android/Windows 近距离路线

目标是保留主要上网连接，并在附近设备间直接交换内容。校园网 AP 隔离只会
限制经该 AP 的路径，单独建立的蓝牙/Wi-Fi Direct 链路可不经过它。

先做只读能力检测：Windows 蓝牙适配器、BLE 角色、RFCOMM、无线网卡与驱动
Wi-Fi Direct 能力；Android BLE 广播/扫描、经典蓝牙和 Wi-Fi P2P/Aware 支持。
Windows 可能没有蓝牙，USB 无线网卡也不保证支持并发角色，必须显示明确降级。

推荐顺序：

1. BLE 做用户主动开启的限时发现和协商，避免长期广播身份信息。
2. Wi-Fi Direct 承担文件；在 Win10、Win11 和具体 USB 网卡上分别验证与
   原有 Wi-Fi 的并发、DHCP、路由和代理行为。不能仅凭系统版本承诺可用。
3. 经典蓝牙 RFCOMM 可作为文字和较小文件的独立通道，吞吐与功耗需实测。
4. 不支持时保留已有 LAN 模式和显式网页节点模式；不静默切换或改默认路由。

“保留上网连接”不等于没有无线资源消耗。Wi-Fi Direct 可能复用同一网卡的
射频时隙；蓝牙也可能与 2.4 GHz Wi-Fi 共存干扰，需用实际延迟、吞吐和耗电
验收。先做 Android↔Windows，再扩展多设备会话。

本阶段用户手机不在测试窗口，Windows 未在线：未使用 ADB、未开启设备发现、
未扫描或改动 OrangePi 上连接测力设备的有线 LAN。真实硬件验证仍待进行。
